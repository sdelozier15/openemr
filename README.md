# med-reconciliation

Python microservice for event-triggered medication reconciliation in OpenEMR. Two API triggers, one combined note, AMC checkbox via direct database insert.

---

## How it works

```
Clinician clicks "Edit medications"
        │
        ▼
GET /baseline/{patient_id}
        └─ GET /fhir/MedicationRequest?status=active
           Before-snapshot → returned to frontend, held in memory
           Nothing visible to clinician
        │
        ▼
Clinician edits medications normally
(add / stop / change via OpenEMR's own dialog boxes)
No API calls fire. Clinician is uninterrupted.
        │
        ▼
Clinician clicks X to close medication list
(dlgopen onClosed callback fires)
        │
        ▼
POST /diff/{patient_id}  +  baseline snapshot in body
        └─ GET /fhir/MedicationRequest?status=active,stopped&_sort=-date
           Diff: baseline vs post-close state
           Single combined note built (audit + patient-readable)
        │
        ▼
Panel ALWAYS appears — even if no changes found
        │
        ├─ Change rows shown (stopped / changed / added)
        ├─ Single pre-filled note shown — clinician edits if needed
        └─ "Confirm & sign" button
        │
        ▼
Clinician clicks "Confirm & sign"
        │
        ▼
POST /submit/{patient_id}
        │
        ├─ POST /api/patient/{pid}/encounter/{eid}/soap_note
        │       Note → Visit Summary · authorized=1 · audit-ready
        │       Satisfies MIPS / TJC documentation requirements
        │
        └─ INSERT INTO amc_misc_data (direct DB — Option 1)
                amc_id='med_reconc_amc' · map_category='form_encounter'
                Checks "Medication Reconciliation Performed?"
```

## Endpoints

| Method | Path | Trigger | Description |
|--------|------|---------|-------------|
| `GET` | `/baseline/{patient_id}` | Med list **opens** | Captures before-snapshot. Silent. |
| `POST` | `/diff/{patient_id}` | Med list **closes** | Runs diff, builds note, returns panel data. |
| `POST` | `/submit/{patient_id}` | Clinician **confirms** | Writes soap note + checks AMC checkbox. |
| `GET` | `/health` | — | Liveness check. |

## The single note

One note is generated by `build_attestation_note()` and serves two purposes:

**Clinical / audit section** (top) — satisfies MIPS and TJC requirements:
- Patient identity, encounter, date, clinician
- Numbered list of changes with type (ADDED / STOPPED / CHANGED) and clinical detail
- Formal attestation statement
- Clinician signature line

**Patient-readable section** (bottom) — plain language for the patient:
- "For Your Records" heading
- Grouped by stopped / adjusted / new medications
- Contact your care team prompt

Both sections live in the same string. One `POST /soap_note` call. No DocumentReference needed.

## The AMC checkbox

**Why it needs a direct DB write:** The "Medication Reconciliation Performed?" checkbox is stored in the `amc_misc_data` table, not in `form_encounter`, and is not exposed through any OpenEMR REST or FHIR endpoint. This was confirmed from the OpenEMR source:

- `library/amc.php` — `amcAddForce()` writes directly to `amc_misc_data`
- `sql/database.sql` — `med_reconc_amc` is the registered rule ID, ONC code `170.302(j)`
- `interface/patient_file/encounter/forms.php` — reads it via `amcCollect("med_reconc_amc", ...)`

**Option 1 (implemented):** Direct INSERT into `amc_misc_data`, replicating exactly what `amcAddForce()` does. Requires `OPENEMR_DB_*` env vars and `aiomysql`.

**Option 3 (preferred if available):** Open the encounter in your OpenEMR instance, check the box manually, and watch the DevTools network tab. If an AJAX call fires, replicate that endpoint instead. Update `amc.py` if you find it — it avoids direct DB access.

## Frontend integration (SMART app)

```javascript
let baselineSnapshot = [];

// TRIGGER 1: fires silently when clinician clicks "Edit medications"
document.querySelector('#edit-medications-btn').addEventListener('click', async () => {
  const res = await fetch(
    `/baseline/${patientId}?encounter_id=${encounterId}`,
    { headers: { Authorization: `Bearer ${token}` } }
  );
  const data = await res.json();
  baselineSnapshot = data.snapshot;  // held in memory

  // Open OpenEMR's medication dialog as normal
  dlgopen('/interface/patient_file/medication_list.php', '_blank', 900, 600, '', '', {

    // TRIGGER 2: fires when clinician clicks X to close
    onClosed: async () => {
      const diffRes = await fetch(
        `/diff/${patientId}?encounter_id=${encounterId}&clinician_name=${encodeURIComponent(clinicianName)}`,
        {
          method: 'POST',
          headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
          body: JSON.stringify(baselineSnapshot),
        }
      );
      const diff = await diffRes.json();
      showReconciliationPanel(diff);  // panel always appears
    }
  });
});

// SUBMIT: fires after clinician clicks "Confirm & sign"
async function handleConfirm(noteText) {
  await fetch(`/submit/${patientId}`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      encounter_id: encounterId,
      patient_id: patientId,
      note: noteText,
    }),
  });
}
```

## Key design decisions

**Why one note?**
A single note that contains both the clinical attestation and a patient-readable summary satisfies MIPS/TJC audit requirements without needing a separate DocumentReference. There is no rule that requires two documents — auditors look for documentation evidence, not a specific format. One well-structured note posted to the soap_note endpoint as `authorized=1` is sufficient.

**Why direct DB for the AMC checkbox?**
`amc_misc_data` is not exposed through any REST or FHIR endpoint. The internal PHP `amcAddForce()` function writes to it directly, and Option 1 replicates that exact operation. If a DevTools inspection of your instance reveals an AJAX endpoint, prefer that instead (see `amc.py` comments).

**Why is the microservice stateless?**
The frontend holds the baseline snapshot in memory between the two triggers. This means the service works correctly across restarts, scaled instances, and load balancers with no shared cache.

**Why does the panel always appear even with no changes?**
The clinician reviewed the list — that IS the reconciliation, regardless of outcome. Always showing the panel ensures the AMC checkbox is only checked after explicit clinician confirmation, and the patient always receives documentation.
